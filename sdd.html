1.3. Project Introduction

FoodFlow is a complete food delivery system that works for customers, restaurants, riders, and admins. It uses simple server calls and keeps the user interface fast and easy.

Instead of forcing users to refresh the page, FoodFlow checks for new updates in the background and shows fresh information to each portal automatically.

Key Innovations: Easy login tokens for each role, fast rider assignment, live kitchen alerts, star rating updates, and a clean modern dashboard look.

Meal Subscription Model — Problem Statement & Proposed Solution

Many customers must place orders every day for regular meals. This is repetitive and time-consuming for office workers, students, and busy families. Restaurants also struggle to predict daily demand.

Proposed solution: FoodFlow adds a Meal Subscription Model so customers can subscribe to weekly or monthly meal plans (breakfast / lunch / dinner). Restaurants create plans with menu items, delivery timing, and price. Subscribed deliveries are scheduled automatically, with options to pause, reschedule, or add delivery notes.

  • Customers: convenience, time savings, flexible scheduling.
  • Restaurants: recurring revenue, better forecasting, higher retention.
  • Riders: predictable routes and scheduled pickups.

1.4. Core Objectives

The system was designed and verified against four primary development objectives:

  1. Architectural Cohesion: Connect all users with one reliable system so each role works in the right place.
  2. Algorithmic Integrity: Keep ratings and rider fees updated automatically and correctly.
  3. Performance Optimization: Make pages load fast and work well in the dashboard without errors.
  4. Security Rigor: Keep users in their correct role and stop bad input or wrong access from breaking the app.

2. System Design (SDD) Specifications

Core data structure, folder layout, and API routes

2.1. Executive Summary & Problem Statement

FoodFlow solves common delivery problems by giving each user portal a clear and connected experience. Customers, restaurants, riders, and admins can work together smoothly.

Normal delivery systems are slow and hard to manage. Customers often wait for updates, restaurants have to coordinate riders by hand, and riders do not see their earnings clearly.

FoodFlow fixes these problems with one simple shared app:

  • Unified Login Tokens: One login system sends each user to the right portal and keeps them signed in safely.
  • Live Update System: Dashboards check for new updates every few seconds, so users see fresh order and delivery information without reloading.
  • Simple Login State Tracking: The app uses tokens to track login state without storing extra session data on the server.
  • Security Center: The admin panel watches for bad activity and can block IPs or force logout when needed.

2.2. Functional Scope & Portals

2.2.1. Customer Portal Workspace

Customers see a clean ordering page with a dark theme. They can choose restaurants, add food to the cart, see the total with the Rs. 150 delivery fee, and track their order status with star ratings.

2.2.2. Restaurant Kitchen Dashboard

Restaurants can update their profile, manage menu items, and handle incoming orders. When a new order arrives, the app shows a clear alert. Ready orders can be sent to online riders from a list.

2.2.3. Rider Fleet Ledger & Dispatch Automation

Riders use a dashboard that gives them a queue number when they go online. After delivering an order, the rider earns Rs. 150, their delivery count goes up, and the app puts them offline so the next rider gets a fair turn.

2.2.4. Central System Governance & Security Dashboard

Admins watch users, stores, orders, and revenue in real time. They can approve new restaurants, set cities, manage categories, and use the security view to see suspicious activity and block threats.

2.6. Order Operational Flow

The system follows a clear flow from order placement to customer feedback:

  1. Order Initiation: Customer completes checkout. The order is marked as pending and shown to the restaurant.
  2. Order Acceptance: Restaurant gets an alert, accepts the order, and updates it to preparing and then ready.
  3. Rider Allocation: Restaurant picks an online rider in the same city and sends the order to them.
  4. Delivery Phase: The rider picks up the order and marks it as delivered when it reaches the customer.
  5. Wallet, Payout & Re-queueing: After delivery, the rider earns Rs. 150, gets credit for the order, and is set offline so the next rider gets a fair turn.

2.7. Security Center & Threat Auditing Flow

The platform tracks suspicious activity and logs important events:

  1. Request Auditing: Every API request is logged and counted so the system knows who is making requests.
  2. Threat Detection: If someone tries to use an admin route without permission, the system records it as a security event.
  3. Security Response: The admin view shows these issues right away and lets admins block the IP or force logout to stop the bad activity.

2.8. Subscription Meal Delivery Service Architecture

The platform supports recurring meal plans, such as weekly lunch or monthly diet subscriptions, with a clear delivery workflow:

  1. Plan & Menu Creation: Restaurants set up recurring meal plans and daily menus, like Monday salad or Tuesday bowl.
  2. Subscriber Approval & Schedule Generation: Customers request a plan. After approval, the system creates every delivery schedule automatically.
  3. Batch Kitchen Dispatch: The kitchen marks meals as ready, groups them by area, and assigns them to one rider.
  4. Rider Multi-Dropoff & Offline Re-queueing: The rider gets one batch with all delivery stops. After finishing the batch, the rider goes offline and must come online again to get a fair new queue number.

2.9. Future Enhancements

  • Bidirectional WebSockets: Use live socket updates instead of checking for changes every few seconds.

6. Security Architecture & Resolved Bug Fixes

Security protections, fixes, and bug corrections

6.1. Implemented Architectural Controls

Bcryptjs Hashing (10 Rounds)

Passwords are turned into secure hashes before saving so the raw password is never stored in the database.

Token RBAC Interceptor middle-tier

Private routes check the user's role in their token so only the correct users can access them.

Query Projection Constraints

Database responses hide password fields so secret data is not sent back to the browser.

6.2. Threat Modeling & Vulnerability Mitigation Plan

We analyzed the current system structure against common vulnerabilities and defined clear mitigation plans:

1. Client-Side JWT Storage (XSS Risk)

Vulnerability: Access tokens are currently saved in browser localStorage, making them susceptible to theft via Cross-Site Scripting (XSS) attacks.

Mitigation Plan: Migrate token storage from localStorage to **HttpOnly, Secure Cookies**, which prevents access via JavaScript and neutralizes script-based session theft.

2. Lack of Authentication Rate Limiting

Vulnerability: The login route permits unlimited connection attempts, exposing user accounts to automated dictionary and brute-force cracking tools.

Mitigation Plan: Integrate an active rate limiter like express-rate-limit to restrict logins to a maximum of 5 attempts within a 15-minute window per IP.

3. Absence of Strict Input Schema Validation

Vulnerability: Loose schema definitions allow potential attackers to pass NoSQL operator objects (such as $ne) to query fields.

Mitigation Plan: Enforce strict request body structures using validators like Joi or express-validator before executing queries.

4. Broken Access Control — Customer Order Data Exposure

Vulnerability: The endpoint GET /api/customer/order/:id returns an order by ID without verifying that the authenticated customer owns that order.

Location: server/routes/customer.js (Lines 95–101)

Why this matters: An attacker can enumerate or guess order IDs and retrieve other customers' order details, including delivery address, phone number, order items, and status.

INSECURE CODE (BEFORE) 
// ❌ VULNERABLE: No ownership check
router.get('/order/:id', authMiddleware, async (req, res) => {
  try {
    const order = await Order.findById(req.params.id)
      .populate('restaurantId')
      .populate('items.menuItemId');
    
    if (!order) return res.status(404).json({ error: 'Order not found' });
    
    // Returns ANY order without checking if it belongs to THIS customer!
    res.json(order);
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});
SECURE CODE (AFTER)

Mitigation Plan: Enforce ownership checks by comparing order.customerId against req.user.id before returning the response. 

// ✅ FIXED: Verify customer ownership
router.get('/order/:id', authMiddleware, async (req, res) => {
  try {
    const order = await Order.findById(req.params.id)
      .populate('restaurantId')
      .populate('items.menuItemId');

    if (!order) {
      return res.status(404).json({ error: 'Order not found' });
    }

    // ✅ SECURITY CHECK: Verify this order belongs to the authenticated customer
    if (order.customerId.toString() !== req.user.id.toString()) {
      return res.status(403).json({ error: 'Access denied' });
    }

    res.json(order);
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

5. Token Secret Problem — JWT Secret Fallback

Vulnerability: The current login code uses process.env.JWT_SECRET || 'secret'. If the environment secret is missing, the app falls back to a weak hardcoded value.

Why it matters: A weak or missing secret makes JWT tokens easy to guess, and stolen tokens can be forged by attackers.

INSECURE CODE (OLD) 
const token = jwt.sign({ id: user._id, role: user.role }, process.env.JWT_SECRET || 'secret');

5. Token Secret Fix — Strong Secret and Token Expiry

Fix: Require a real secret from the server environment and make tokens expire after a short time.

SECURE CODE (NEW) 
const secret = process.env.JWT_SECRET;
if (!secret) {
  throw new Error('JWT_SECRET is required');
}
const token = jwt.sign(
  { id: user._id, role: user.role }, 
  secret,
  { expiresIn: '1h' }
);

Easy explanation: Always use a real secret from your server settings, never a default value, and make tokens stop working after some time so stolen tokens are less useful.

Vulnerability: Some API routes accept fields like name, price, and description without checking their types or presence.

7. Authentication & Identity Failure — Role Mismatch

Vulnerability: The login system may accept a valid user but not always check if they are using the correct portal for their role.

Why this matters: If a restaurant or rider logs in through the wrong portal, they may gain access to pages or actions that should be denied.

INSECURE CODE (OLD) 
const user = await User.findOne({ email });
if (!user || !(await bcrypt.compare(password, user.password))) {
  return res.status(401).json({ error: 'Invalid credentials' });
}
// Missing strict portal role check for restaurant / rider pages

7. Auth Fix — Verify Portal Role Before Login

Fix: Always check the requested portal role and reject the login if the user's role does not match.

SECURE CODE (NEW) 
const user = await User.findOne({ email });
if (!user || !(await bcrypt.compare(password, user.password))) {
  return res.status(401).json({ error: 'Invalid credentials' });
}
if (portal === 'restaurant' && user.role !== 'restaurant') {
  return res.status(403).json({ error: 'Use the restaurant login page' });
}
if (portal === 'rider' && user.role !== 'rider') {
  return res.status(403).json({ error: 'Use the rider login page' });
}
// Continue only if portal and role match
return res.json({ token, user });

Easy explanation: If someone logs in through the restaurant page, make sure they are really a restaurant user. If not, block them and keep roles separate.
